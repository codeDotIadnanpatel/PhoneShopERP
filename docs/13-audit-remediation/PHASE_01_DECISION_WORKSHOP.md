## 3. What changed since the Phase 00 review (DP-01 … DP-15)

Plain-English resolution of every finding. Full text is in each paper's revision log.

| DP | The problem, in plain English | Resolution adopted in revision 2 | Cost / consequence |
|---|---|---|---|
| **DP-01** | The type rules banned fixed-width `char` columns, then required `char(3)` for currency | Currency is `text` with an uppercase-3-letter check and a foreign key to the currency table. `char` stays banned — it pads values with spaces and causes surprising comparisons | None; same storage size for 3-letter codes |
| **DP-02** | One paper put global data in a table with no tenant column; another allowed a "global" row with an empty tenant column. Empty-tenant rows are invisible to RLS and break tenant-safe foreign keys | Three clearly separated classes: vendor reference data (no tenant column, no RLS), tenant infrastructure (tenant column, RLS), platform security records (no tenant data, restricted role). **No nullable tenant column anywhere.** Tenant-extensible data is copied per tenant at setup | A few extra rows per tenant at provisioning; removes a whole class of isolation bugs |
| **DP-03** | The key rule said "never generated by the client", but the offline POS must create records while disconnected | UUIDv7 is generated by the owning application: the server online, or the approved offline client. Never by a database default, never ad-hoc in a screen. The server validates the identifier and the tenant | Requires an ID-validation test; offline sync keeps working without ID remapping |
| **DP-04** | The proposal presented EF Core query filters as if they were the security mechanism, but no ORM had been chosen | Security is the database policy plus one enforced transaction boundary. The ORM is an engineering choice and cannot weaken the guarantee | Engineering team picks EF Core/Dapper; the same security tests run either way |
| **DP-05** | Permission cache version was stored per user, but roles belong to a user *within a tenant*. A user in two tenants would invalidate the wrong cache | Version lives on the membership (tenant users) or platform grant (operators). Changing roles in one shop cannot affect another | None; removes a stale-permission bug |
| **DP-06** | Login needs a tenant to look up permissions, but the membership lookup itself is protected by tenant isolation — a circular dependency. Multi-tenant users could not log in as written | Membership is the single table readable before a tenant exists, and only for the logged-in user's own rows. The tenant is then chosen explicitly and stored on the session | One deliberate, tested exception to "tenant context first" |
| **DP-07** | Audit data sat in a schema described as having no RLS, so any tenant could potentially read another tenant's audit trail | Audit is tenant-isolated for reads and append-only. Pre-login events with no known tenant go to a separate platform-only security log containing no business data | One extra table; audit isolation test required |
| **DP-08** | Forced RLS applies to the table owner, but the migration role had no documented way to run data fixes | Schema changes are unaffected by RLS. Data backfills run one tenant at a time with tenant context set, enumerating tenants through one restricted function. RLS is never switched off | Backfills are slightly slower and must be written per tenant |
| **DP-09** | Policies call a helper function but the grants needed to execute it were never stated | Explicit grant list for schema usage, helper execution, reference reads and append-only audit inserts; `PUBLIC` gets nothing | None; without it, policies fail with a permission error |
| **DP-10** | Signing keys, key publication and rotation were not addressed | Managed provider owns keys; our API caches published keys, refreshes on an unknown key id, and fails closed. Self-hosted fallback responsibilities and emergency rotation are documented | Operational runbook item; no code in Phase 01 beyond key validation |
| **DP-11** | "Tenant switching" was named but never defined — a risk of a live session changing scope in place | Switching is an explicit, audited operation that ends the old session and creates a new one. Tokens never carry a tenant | One extra endpoint and test; no scope-mutation risk |
| **DP-12** | MFA was triggered by permission strings that the repository says are not final | Trigger is the permission catalogue's `risk_class`, not hard-coded names. Named permissions are labelled illustrative | Phase 01 must add `risk_class` to the catalogue |
| **DP-13** | The RLS helper's language and volatility were unspecified, with a possible per-row performance cost | `STABLE`, schema-qualified, execution revoked from `PUBLIC`; benchmark required; documented inline fallback for the hottest tables | A benchmark note, no user-visible effect |
| **DP-14** | Row version was maintained by the application, so raw SQL or a migration could silently overwrite a concurrent edit | A database trigger increments the version on every update. A stale update still affects zero rows and returns `409` | One small trigger per mutable table |
| **DP-15** | Device registration appeared in the shared platform schema in one paper and as an identity concern in another | Device registry lives in the identity module; device-trust detail stays with D-013 | None; removes an ownership ambiguity |

## 4. The single architecture the three papers now describe

| Concept | Single agreed rule | Where it is defined |
|---|---|---|
| Database roles | `erp_owner` (no login, owns objects), `erp_migrator` (migration job only, no bypass), `erp_app` (runtime, no DDL, no bypass), `erp_platform_admin` (audited bypass) | D-001 R7 |
| Schemas | One per module plus `platform`; `platform` has three object classes with different rules | D-003 R1 |
| Tenant column | `tenant_id uuid NOT NULL` on tenant-owned tables; never nullable; never a "global" row inside a tenant table | D-001 R2, D-003 R3 |
| Tenant context | Transaction-local `app.tenant_id` + `app.user_id`; missing context raises; one table readable pre-tenant (own memberships) | D-001 R4/R5/R8a |
| Tenant identity source | Server-side session record; never a request field, never a token claim | D-001 R8, D-002 R1 |
| Keys | UUIDv7 from the owning application (server or approved offline client); no database default; parent tables expose `(tenant_id, id)` unique | D-003 R3 |
| Concurrency | `row_version` incremented by a trigger; stale write → `409` | D-003 R5 |
| Audit | `platform.audit_event` tenant-isolated and append-only; `platform.security_event` platform-only, no tenant business data | D-001 R12 |
| Permission version | Per membership (tenant) or per platform grant, not per user | D-002 R5 |
| Tenant switch | New session, old refresh token family revoked, audited | D-002 R5a |
| Device registry | `identity.device`, owned by the identity module; detail in D-013 | D-002 R3, D-003 R1 |
| Session/token | Token carries `sub` + `sid` only; tenant and permissions come from the server | D-002 R1 |

## 5. Decision 1 — D-003 Physical database conventions

**The question:** Do we adopt one PostgreSQL schema per module with a shared `platform` schema,
UUIDv7 identifiers generated by the application, tenant-safe composite foreign keys, and
SQL-first reviewed migrations?

**Recommendation:** yes, as revised in D-003 revision 2.

**Why it matters in practice.** Every module gets its own named area (`inventory.sale`,
`accounting.journal`). The database itself refuses a row that references another tenant. Keys can
be created on a disconnected POS without asking a server. Migrations are reviewed SQL, so the
row-level security rules are visible in the same change as the table they protect.

**Alternatives and their consequences:**

| Alternative | What you gain | What it costs |
|---|---|---|
| Single `public` schema with table prefixes | Simplest to start | No per-module permissions; extraction later requires a disruptive schema split; harder to see cross-module access |
| Database per module | Strongest separation | Cross-module transactions and reporting become distributed-systems problems; contradicts the modular-monolith decision |
| `bigint` identity keys | Smaller indexes, simple | Offline creation needs a second ID scheme and remapping; sequential IDs leak volume |
| EF Core migrations as the default | Less SQL writing | Row-level security, grants and triggers still need raw SQL, so the reviewed artifact stops matching the executed one |

**Implementation consequences:** the first migration also creates roles, helper functions and the
reference tables. CI gains a clean-database migration job, a naming/type lint and a drift test if
EF Core is used for mapping.

**Long-term and scaling:** tenant-leading indexes keep RLS queries fast. Composite tenant keys add
one index per parent table; that index also serves the common tenant-scoped lookup, so the cost is
mostly recovered. UUIDv7 keeps new rows physically clustered, which matters on large movement and
audit tables. Partitioning is explicitly deferred until measured.

**Specialist review:** internal Architecture + Data review is required. No external specialist is
needed to approve the conventions; a database-engineer review of the first real migration and its
index plan is recommended before Phase 02.

## 6. Decision 2 — D-001 Tenant context and RLS

**The question:** Do we isolate tenants with forced PostgreSQL row-level security driven by a
transaction-local tenant setting, keep tenant identity in the server-side session, and use the
four-role least-privilege model?

**Recommendation:** yes, as revised in D-001 revision 2.

**Why it matters in practice.** Even if an application bug forgets a filter, the database returns
only the current tenant's rows. The setting disappears when the transaction ends, so a pooled
connection cannot hand one shop's context to the next. If the setting is missing, the query fails
loudly instead of returning nothing.

Two clarifications that changed in revision 2 and are worth your attention:

1. **The tenant is not carried in the login token.** It lives on the server-side session. Removing
   someone from a shop therefore takes effect within the 60-second session cache, not when their
   token expires.
2. **The user's own membership list is the only thing readable before a tenant exists.** Without
   that single exception, a user who belongs to two shops could not log in at all.

**Alternatives and their consequences:**

| Alternative | What you gain | What it costs |
|---|---|---|
| Application filtering only (no RLS) | Fastest to build | One missed filter is a full cross-tenant breach; contradicts the security baseline |
| Session-level setting instead of transaction-local | No need to wrap every read in a transaction | A crash or bug leaves the setting on a pooled connection — a silent cross-tenant leak |
| One database role or schema per tenant | Stronger isolation | Role/schema explosion for thousands of small shops; migration fan-out; higher cost |
| Branch-level rules inside the database too | Database backstop for branch mistakes | Every cross-branch workflow needs policy exceptions; owner and consolidated reports become complex. Branch scope stays in application authorization, tested separately |

**Implementation consequences:** every tenant-scoped operation runs inside a transaction; every
tenant-owned migration ships its policy, grants and version trigger together; jobs and exports
iterate tenant by tenant.

**Long-term and scaling:** policies are tenant-invariant, so query plans stay stable. The model
scales to thousands of tenants without per-tenant DDL. Transaction-local context works with
PgBouncer transaction pooling, which keeps connection costs low.

**Specialist review:** internal Security + Architecture review is required. External penetration
testing is required **before the pilot**, not before Phase 01. The one area worth an experienced
PostgreSQL reviewer's time is the fail-closed helper and the pooled-connection leakage test.

## 7. Decision 3 — D-002 Identity and session lifecycle

**The question:** Do we use a managed standards-based identity provider behind our own adapter,
with short-lived tokens backed by a server-side session registry, server-resolved permissions, and
a signed offline authorization snapshot for the POS?

**Recommendation:** approve the approach. Vendor selection can be delegated with a deadline,
because the adapter boundary makes the vendor replaceable.

**Why it matters in practice.** The identity provider does the security-critical work — password
storage, MFA, passkeys, breach detection — that a small team should not hand-roll. Our system
still decides who belongs to which shop and what they may do. A stolen POS can be revoked
centrally. Permission changes take effect within the cache window instead of waiting for a token
to expire.

**Alternatives and their consequences:**

| Alternative | What you gain | What it costs |
|---|---|---|
| Build identity in-house (`ASP.NET Core Identity` + OpenIddict) | No per-user fee; one stack | We own password hashing, MFA enrolment, token rotation, breach response and recovery abuse — the highest-risk area to hand-roll |
| Self-hosted Keycloak | Control and no per-user fee | We operate a security-critical service: HA, upgrades, key management, patching |
| Long-lived JWT with no server session | Simplest and cheapest | A stolen device cannot be revoked promptly — unacceptable for a shop POS |
| Per-tenant bring-your-own identity provider | Attractive to chains | Enterprise-only complexity with no small-shop value; deferred to Phase 09+ |

**Implementation consequences:** an identity module owns users, memberships, sessions and the
device registry; login becomes a runtime dependency with an outage runbook; MFA and step-up
become permission-catalogue driven; the POS receives a signed, expiring offline snapshot.

**Long-term and scaling:** per-active-user cost is the main commercial risk. It is bounded by the
cost ceiling you set, and the adapter means a provider change is an adapter change, not a rewrite.
Session records grow with logins; they are small, and retention is a later decision (D-016).

**Specialist review:** Security review is required. Legal/commercial review is required for the
provider contract and data-residency terms when the vendor is selected. No external identity
architect is needed to approve the design.

## 10. Risks of proceeding, and how revision 2 reduces them

| Risk | Effect if unmanaged | Mitigation now in the papers |
|---|---|---|
| A missed tenant filter leaks data | Reputational and legal damage | Forced RLS, composite tenant FKs, cross-tenant negative tests |
| Stale permissions after a role change | Removed staff retain access | Per-membership version, ≤60 s cache, always re-check for privileged actions |
| Offline POS cannot create valid records | Core product requirement fails | UUIDv7 generated by the approved offline client; server validates |
| Migration cannot fix data under forced RLS | Deployment blocked or RLS disabled in a hurry | Per-tenant backfill procedure; RLS is never disabled |
| Audit trails become a cross-tenant leak | Sensitive operational data exposed | Tenant-scoped audit reads, append-only grants, separate platform security log |
| Vendor lock-in or per-user cost shock | Pricing model breaks | Adapter boundary, cost ceiling, replaceable provider |
| Over-engineering delays Phase 01 | Slow start | Phase 01 backlog is scoped to platform foundations only; no business module |
